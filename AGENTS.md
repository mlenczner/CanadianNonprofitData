# Canadian Nonprofit Data

Links federal Grants & Contributions (`grants.csv`), the CRA T3010 charity registry (`data/t3010/`), Canada Council for the Arts grants (`data/canada_council_grants.csv`), and Ontario Trillium Foundation grants (`data/otf_grants.csv`) into one entity graph in `nonprofit_network.duckdb`, built by `analysis/build_entity_graph.py`. See `docs/entity-resolution-methodology.md` for the matching approach and match-rate results.

## Setup & commands

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements-dev.txt   # requirements.txt (runtime) + pytest (dev/test)
```

Build the entity graph (fetches T3010 + Canada Council + OTF data first, then links everything):

```bash
.venv/bin/python analysis/download_sources.py
.venv/bin/python analysis/build_entity_graph.py
```

Run tests:

```bash
.venv/bin/python -m pytest tests/
```

## Rule: never read the raw data files directly

`grants.csv` (~2GB), `nonprofit_network.duckdb`/`.wal`, everything under `data/t3010/` (48 files, 12 years × 4 kinds), and `data/otf_grants.csv` (~28MB, 32,842 rows) are large or numerous enough that they should never be read directly — **always query via DuckDB aggregates**, e.g.:

```bash
.venv/bin/python -c "import duckdb; con = duckdb.connect('nonprofit_network.duckdb', read_only=True); print(con.execute('SELECT ... LIMIT 20').fetchall())"
```

## Table schemas (`nonprofit_network.duckdb`)

**`entities`** — one row per resolved organization
- `entity_id` INTEGER, `bn_root` VARCHAR (9-digit CRA business number root, nullable), `canonical_name` VARCHAR, `city` VARCHAR, `province` VARCHAR, `entity_kind` VARCHAR (`charity` / `federal_dept` / `funder_org` / `other_org`), `bn_full` VARCHAR (nullable — full 15-char BN with program-account suffix, e.g. `119219814RR0001`; sourced from `raw_t3010_ident.BN`, latest `source_year` row per `bn_root`; only populated for entities with an identification-schedule row on file, i.e. registered charities), `search_name` VARCHAR (`canonical_name` lowercased + accent-stripped via DuckDB's native `strip_accents()` + whitespace-collapsed — powers `webapp.py`'s accent-insensitive live search)

**`entity_links`** — audit trail of every match decision
- `entity_id` INTEGER, `source_dataset` VARCHAR (`federal_gc` / `canada_council` / `t3010_qualified_donee` / `t3010_non_qualified_donee` / `otf`), `raw_name` VARCHAR, `raw_bn` VARCHAR, `match_method` VARCHAR (`exact_bn` / `fuzzy_accept` / `unmatched_new`), `match_score` DOUBLE (nullable)

**`grants_unified`** — one row per grant/gift from any source
- `grant_id` INTEGER, `source_dataset` VARCHAR, `funder_entity_id` INTEGER, `recipient_entity_id` INTEGER, `amount_cad` DOUBLE, `fiscal_year` INTEGER, `program_name` VARCHAR, `description` VARCHAR (nullable), `source_ref` VARCHAR (nullable — see issue #4 below; only populated for `federal_gc`, `TRIM(owner_org)+"|"+TRIM(ref_number)`)

**`entity_role_summary`** — per-entity give/receive totals and role
- `entity_id` INTEGER, `canonical_name` VARCHAR, `entity_kind` VARCHAR, `total_given` DOUBLE, `total_received` DOUBLE, `n_grants_given` INTEGER, `n_grants_received` INTEGER, `given_share` DOUBLE (nullable), `role` VARCHAR (`primarily_funder` given_share≥0.9 / `primarily_recipient` given_share≤0.1 / `dual_role` / `no_flows`)

**`entity_financials`** — T3010 line-code data joined to entities by BN root
- `entity_id` INTEGER, `bn_full` VARCHAR, `fiscal_period_end` DATE, `total_revenue` DOUBLE (line 4700), `total_expenditures` DOUBLE (4950), `total_expenditures_incl_disbursements` DOUBLE (5100), `total_gifts_to_qualified_donees` DOUBLE (5050), `revenue_from_federal_gov` DOUBLE (4540), `revenue_from_any_cdn_gov` DOUBLE (4570)
- One row per entity: `build_entity_financials` dedups `raw_t3010_fin` to the latest `source_year` per `bn_root` before joining.

**`entity_financials_by_year`** — like `entity_financials`, but every fiscal year instead of only the latest
- `entity_id` INTEGER, `fiscal_period_end` DATE, `fiscal_year` INTEGER, `total_revenue` DOUBLE (4700), `gov_revenue` DOUBLE (4570), `foundation_revenue` DOUBLE (4510, "total received from other registered charities")
- One row per `(entity_id, fiscal_year)`: `build_entity_financials_by_year` dedups `raw_t3010_fin` to the latest `source_year` per `(bn_root, fiscal_year)` before joining. Feeds the org-page funding timeline's declared-vs-identified comparison (see Organization Profile Pages below). Can be rebuilt on its own, without a full pipeline run, via `analysis/build_entity_graph.py --financials-by-year-only` — it only reads `raw_t3010_fin`/`entities`, both already loaded by a prior full build.

**`crowding_out_panel`** — Part A of `docs/crowding-out-and-flow-through-spec.md`: one row per treated org's event year, plus one row per matched control assigned to it
- `bn_root` VARCHAR, `assigned_year` INTEGER (the org's own treatment year if `role='treated'`, or the treated org's year if `role='matched_control'`), `role` VARCHAR (`treated` / `matched_control`), `matched_group_id` VARCHAR (the treated org's `bn_root`; equal to `bn_root` on treated rows), `match_tier` VARCHAR (nullable — `province+decile+trend` / `province+decile` / `province_only`, null on treated rows), `province` VARCHAR, `revenue_decile` INTEGER (line 4700 total revenue at `assigned_year - 1`, NTILE(10) within that year's cross-section), `pre_mean`/`post_mean` DOUBLE (line 4500 donations, 3-year windows around `assigned_year`, the year itself excluded), `pre_n`/`post_n` INTEGER (observed years per window, both required ≥2), `pct_change` DOUBLE, `exact_bn_link` BOOLEAN (nullable — whether the treated org's triggering-year receipt resolved via `entity_links.match_method='exact_bn'`; null on control rows)
- Built by `analysis/crowding_out.py`'s `write_crowding_out_panel`; source is `raw_t3010_fin` line 4500 (not `entity_financials_by_year`, which has no donations column — see that script's module docstring for the open question of whether it should grow one) joined against government receipts (federal G&C + OTF + Canada Council) from `grants_unified`.

**`crowding_out_regression_panel`** — long-format org-year panel feeding `crowding_out.py`'s fixed-effects regression
- `panel_unit_id` VARCHAR (`bn_root || '_Y' || assigned_year` — a stacked-regression unit key, since the same org can be a matched control for more than one treated org's event year), `bn_root` VARCHAR, `Y` INTEGER (assigned event year), `treated` INTEGER (0/1), `fiscal_year` INTEGER, `donations` DOUBLE, `post` INTEGER (0/1), `log_donations` DOUBLE
- One row per `(panel_unit_id, fiscal_year)` with a positive donations value in `[Y-3, Y+3]`, `Y` itself excluded. Feeds `pf.feols("log_donations ~ treated:post | panel_unit_id + fiscal_year", ...)`, SEs clustered on `bn_root`.

**`flow_through_chains`** — Part B of `docs/crowding-out-and-flow-through-spec.md`: one row per intermediary→donee regrant edge
- `hop1_source_datasets` VARCHAR (comma-joined, e.g. `federal_gc,otf`), `hop1_amount` DOUBLE, `hop1_fiscal_year` INTEGER (all three carried from the chain's root intermediary, not the current edge's node), `intermediary_bn_root` VARCHAR, `intermediary_entity_id` INTEGER (nullable), `hop_depth` INTEGER (1 = direct from the hop-1-funded root intermediary; 2 = a further regrant from a donee who is itself a large regranter — capped at 2, i.e. 3 hops total counting the hop-1 government receipt), `donee_bn_root` VARCHAR (nullable), `donee_entity_id` INTEGER (nullable), `donee_raw_name` VARCHAR, `donee_raw_bn` VARCHAR, `hop2_amount` DOUBLE, `hop2_fiscal_year` INTEGER, `is_cycle` BOOLEAN (donee's `bn_root` already appears earlier in its own chain; traversal stops there without recursing further)
- Built by `analysis/flow_through.py`'s `write_flow_through_chains`. An "intermediary" is a `(bn_root, fiscal_year)` where T3010 line 5050 (total gifts to qualified donees) exceeds $100k in a year overlapping (same calendar year as) a hop-1 government receipt for the *root* node only — a depth-2 regranter only needs to independently clear the line-5050 bar itself (`large_regranters_by_year`), since it received its money from the depth-1 intermediary, not from government directly. Donee BN resolved to `entities.bn_root` via the same inline `substr(regexp_replace(...))` shortcut used elsewhere, not the more careful Python `normalize_bn()`. Counts are co-occurrence, not dollar-tracing — see the script's "honest denominator" framing.

## BN hygiene and entity-merge review queues

Raw BNs across every source (`entity_links.raw_bn`, T3010 identification/donee schedules, `grants.csv`) arrive in many formats (`132162041RT0001`, `ARC 132162041 RT 0001`, bare 9-digit, period/hyphen-punctuated). `normalize_bn()` parses these to a 9-digit root but deliberately never repairs or guesses at one (see its docstring) — a corrupted-but-plausible BN (e.g. a leading zero gained/lost when some upstream system treated a BN as a number) mints its own entity rather than silently merging into the real one. `bn_reject_shape()` buckets every non-blank raw BN that failed to parse (by digit count / non-numeric), printed in the build report so new/unexpected formats surface rather than disappearing into one opaque count.

Two mechanisms handle the entities this leaves split, both run in `main()` right after `build_entities_and_grants()` (before `build_role_summary()`/`build_entity_financials*()`, so those aggregates reflect the merged state without a second full rebuild):

- **Automatic (conservative, applied every build):** `build_null_province_residual_merges()` bridges a residual-dedup gap — two records of the same org, one with a real province on file and one blank, mint two separate `other_org` entities even when their `normalize_name()` keys are byte-identical (the residual dedup key is `(normalize_name(name), province)` and can't bridge a NULL province). Merges the blank side into its name-identical twin only when there's exactly one such twin and the twin carries a `bn_root` or `province`; skips generic-looking short names; never merges two BN-bearing entities or merges into a `charity`-kind entity.
- **Human-gated (review CSVs, no auto-merge):** `build_bn_near_miss_review()` writes `analysis/output/bn_near_miss_review.csv` — entity pairs whose `bn_root`s are one digit-substitution or leading-digit-shift apart (`_bn_substitution_candidates()`/`_bn_shift_candidates()`) AND whose folded names score ≥ `FUZZY_ACCEPT`. `build_branch_variant_review()` writes `analysis/output/branch_variant_review.csv` — BN-less entities whose name has a trailing " – place" / "(place)" shape over a BN-bearing twin's name (e.g. "Canadian Red Cross – Ottawa" over "THE CANADIAN RED CROSS SOCIETY") — could be a genuine regional entity or the same org's branch office, not distinguishable from name shape alone. Neither queue auto-merges: a wrong BN/branch merge silently combines two different real organizations' money, worse than leaving them split.

Confirmed merges from either review CSV are applied via `data/bn_merge_overrides.csv` (columns: `entity_id_keep`, `entity_id_merge`, `note`; gitignore-exempted like `evidence/l2_classifications.duckdb` — small and hand-maintained, not a fetched dataset), read by `apply_bn_merge_overrides()`, which shares `_apply_entity_merges()` with the automatic path above. **`entity_id`s are only stable within one build** (`Resolver` assigns them in processing order) — re-verify overrides against a fresh rebuild's actual entity_ids before trusting them, don't assume they carry over. `analysis/build_entity_graph.py --apply-overrides-only` applies a newly-edited overrides file (plus refreshes `entity_role_summary`/`entity_financials*`) against an already-built DB without re-running the whole pipeline — same pattern as `--financials-by-year-only`.

**Verified against a real rebuild (2026-07-19).** BN parse-rejects: 56,625 non-numeric, 8,974 10-digit, plus smaller buckets down to 7 17-digit — every one bucketed by `bn_reject_shape()` rather than one opaque count. Entity resolution seeded 536,327 entities; `build_null_province_residual_merges()` applied **26,289 merges** (536,327 → 510,038), the largest by dollar impact being government/institutional funders that had split on a blank vs. filled province (e.g. Government of Ontario, $10.4B moved). Both Fédération acadienne clusters named in the motivating spec (`de la Nouvelle-Écosse` and `culturelle acadienne de la Nouvelle-Écosse`) now resolve to exactly 1 entity each. `build_bn_near_miss_review()` found **2,199 candidate pairs**; `build_branch_variant_review()` found **29,866 candidates** (an intentionally loose, human-reviewed net — most are single small donee-schedule typos, not distinct organizations).

**A real bug found and fixed during this verification pass, not hypothetical:** the near-miss/branch-variant review CSVs' dollar-flow columns were reading a *stale* `entity_role_summary` — `main()` originally called `build_bn_near_miss_review()`/`build_branch_variant_review()` **before** `build_role_summary()`, so a first-ever build would either error (table doesn't exist yet) or, on a DB that already had one from a prior run, silently report leftover numbers from that prior run. Confirmed directly: one entity's near-miss row reported $133,000 while its true post-merge flow (read live from `grants_unified` moments later) was $217,650,891 — two orders of magnitude off. Fixed by moving `build_role_summary()` before both review-queue writers in both `main()`'s full-build path and `--apply-overrides-only`.

**The Canadian Red Cross specifically:** seeded `data/bn_merge_overrides.csv` with the two clearest confirmed pairs from `bn_near_miss_review.csv` — bn_root `011921981` (leading-zero-shifted: `'0' + 119219814[:8]`) and `119218814` (single-digit substitution) both merged into the real charity entity (bn_root `119219814`), bringing it to **$1,121,820,546**. Confirms the near-miss detector itself needed a fix during verification too: scoring the two raw `canonical_name`s (or `search_name`s, which only fold case/accents/whitespace) directly gave ~61 for the real charity's bilingual name (`"THE CANADIAN RED CROSS SOCIETY / LA SOCIETE CANADIENNE DE LA CROIX-ROUGE"`) against a corrupted duplicate's English-only name — well under `FUZZY_ACCEPT` — even though the English half is a 100% match. Fixed with `_best_name_variant_score()`, which runs `name_variants()` (the same bilingual `"/"`-splitter `add_charity()` already uses) on both sides and takes the best pairwise score.

**Two gaps found and left for review, not fixed here (same "flag rather than chase" convention as the open issues below):**
- Two large Red Cross fragments (`CANADIAN RED CROSS SOCIETY`, $501.8M, no BN, province `AB`; `Canadian Red Cross`, $131.8M, no BN, no province) are untouched by any of the four mechanisms above: the $501.8M one carries a *wrong*, non-blank province (its donee-schedule records apparently used the filer's/donation's province, not the charity's real registered `NB`) — not the blank-province gap item 3 fixes — and the real charity's own province-blocked fuzzy candidates never considered it during initial resolution (same class of gap as the pre-existing Prince Rupert Port Authority/Salvation Army cases in issue #3 below). The $131.8M one has no province either but sits in a name cluster with 40+ other BN-bearing `other_org` entities sharing the same normalized name (nearly all near-miss-typo'd BNs) — `build_null_province_residual_merges()`'s single-unambiguous-twin guard correctly declines to guess which one it belongs to.
- **Webapp search ranking regression, confirmed, out of this task's scope (`analysis/build_entity_graph.py` + one rebuild) — flagged for a follow-up in `webapp.py`.** Searching "canadian red cross" does *not* surface the $1.12B real charity entity on page 1: the query matches 26 exact-name ties (tier 0) + 119 prefix matches (tier 1, max flow $501.8M) before ever reaching tier 2, where the real charity sits (its canonical name starts with "THE", not "canadian"). `webapp.py`'s existing `WILDCARD_FLOW_MULTIPLIER` promotion (a prior, separately-landed fix) only compares a lower-tier candidate against *tier 1's* max flow (100×) — it doesn't account for tier 0 also being ahead of it, and $1.12B is nowhere near 100× tier 1's own $501.8M max. This is a real, live gap in that already-landed ranking fix, newly exposed (not caused) by this change consolidating the Red Cross into fewer, larger entities. Not fixed here since it's webapp.py ranking logic, not entity resolution.

## Individual and sole-proprietor recipients are excluded, not just orgs

This app is about nonprofit organizations, not people — but three of the five sources name individuals as grant recipients (e.g. a federal research contribution to a named academic, a Canada Council grant to an individual artist), and until this fix every one of them minted its own entity and org page (confirmed real: `/orgs/mcconnell-joanne`, `/orgs/mcconnell-erin-mcmaster-university`, `/orgs/mcconnell-kathryn` — three different people, unrelated to each other, who happened to share a surname). `main()` in `analysis/build_entity_graph.py` now skips these recipients before `Resolver.resolve()` ever sees them, so no entity is created and the grant itself doesn't appear in `grants_unified` (a funder's `total_given` reflects only its org-to-org flows after this change):

- **federal_gc**: skips `recipient_type == 'P'` ("Individual/Sole proprietor" per the code's own label in `analysis/profile_grants.py`) — 220,176 of ~1.08M raw rows carry this code (profiled directly from `grants.csv`; the real, post-dedup build skipped 69,947, since `raw_grants_latest` collapses amendments first). **`recipient_type` is also blank/NULL for 325,252 raw rows, and real individuals hide in there too** — confirmed real: `"McConnell, Erin (McMaster University)"` and `"McConnell, Jennifer S"` (both real academic-grant recipients) carry no `recipient_type` at all, so they survived the first pass of this fix. `looks_like_individual_name_comma()` catches the `"Lastname, Firstname [Middle] [(Affiliation)]"` shape these take, applied *only* when `recipient_type` is blank (never overriding an explicit non-`'P'` declaration — a spot check of this same shape under explicit `N`/`F`/`G`/`O`/`S`/`A`/`I` codes found a real organization false positive, `"L'Avenue, justice alternative"`, typed `N`, sitting alongside real misclassified individuals like `"Furdyk, Michael"` also typed `N`; an explicit department declaration is a stronger, if imperfect, signal than a blank field, so that bucket is a known, undressed residual gap rather than something this heuristic reaches into). Two guards on the blank-type check itself, both needed by real counterexamples found while sampling all 147,215 distinct blank-`recipient_type` names (28,330 matched after both guards): the token after the comma must start with a capital letter (excludes `"AdMare, centre d'artistes..."` and `"Rouyn-Noranda, ville et village en sante inc."` — real Quebec orgs in "Name, lowercase description" form — at the cost of missing individuals entered all-lowercase, e.g. `"banquy, xavier"`, an accepted residual gap) and must not be a corporate suffix (excludes `"Sumalytics, Inc."`).
- **canada_council**: skips `Recipient Type == 'Individual'` — verified the field's only three values directly from `data/canada_council_grants.csv`: `Organization` (26,953), `Individual` (32,752), `Group` (5,297). `Group` (an informal collective, e.g. a musical/artist collective) is deliberately kept — it's not a single person, and Canada Council's own schema distinguishes it from `Individual`.
- **t3010_non_qualified_donee**: has no recipient-type field at all (CRA's non-qualified-donee schedule is name-only), so `looks_like_individual_donee_name()` detects the shape individual donees take there instead — `"Lastname  Firstname"` (2+ spaces, no comma; a comma an upstream CRA export step apparently drops — confirmed the same person appears as `"McConnell, Joanne"` in Canada Council's data and `"McConnell  Joanne"` here), sometimes with a trailing `"(nickname)"` parenthetical. Sampled all 21,462 distinct raw names across `data/t3010/non_qualified_donees_*.csv`: 5,382 match. Manually reviewed every match for organization-name false positives — found one (`"KCA   Niisaachewan(Dalles)"`, a community name, not a person) out of 5,382, accepted as a rare tradeoff. Deliberately conservative: a single-space two-word name (indistinguishable from a real short org name like "Red Cross") is never flagged, so some individual donees in this source will still slip through unfiltered — a known, accepted residual gap, not chased further here.

**Known residual gaps, not chased further (same "flag rather than chase" convention as elsewhere in this doc):** individuals under federal_gc's explicit non-`'P'` recipient_type codes (see above); individuals entered all-lowercase under a blank federal_gc recipient_type; individual donees in t3010_non_qualified_donee whose name happens to take a single-space two-word shape.

Regression tests: `tests/test_individual_recipient_filter.py` (`looks_like_individual_donee_name()` and `looks_like_individual_name_comma()` against real sampled names from both the individual and organization sides). Takes effect on the next full rebuild.

**`analysis/dbquery.py`** is a small read-only SQL runner (single `SELECT`/`WITH` statement, connection opened `read_only=True`, denylist of write-ish keywords as a second layer of defense) added alongside this fix so routine ad hoc lookups against `nonprofit_network.duckdb`/the raw CSVs can be allowlisted by exact command prefix in `.claude/settings.json` without allowlisting a bare `python -c` (which would be arbitrary code execution). Not a general-purpose tool — one query, no flags; reach for a real script for anything more.

## open.canada.ca WAF workaround

`open.canada.ca` rejects `urllib`'s default request signature but accepts `curl`'s. Both `analysis/download_sources.py`'s CSV downloads and its CKAN API calls (`package_search`/`package_show`) shell out to `curl -sL` rather than using `urllib.request` or `requests`. If adding new downloads from this domain, follow the same pattern.

## Open issues

1. **Silent row drops from `ignore_errors=true`, partially addressed — investigated further, root cause is two unrelated problems, no safe fix found yet.** The multi-year T3010 loads in `load_raw` (`identification_*.csv`, `qualified_donees_*.csv`, `non_qualified_donees_*.csv`, `financials_*.csv`) all use `ignore_errors=true` across 48 files spanning a form whose columns changed over the years (e.g. line codes 5045/5840-5843 only exist from 2023 onward). `_load_t3010_table` scans each file individually with `store_rejects=true` first and prints a per-file reject count (DuckDB doesn't allow `store_rejects` together with `union_by_name`, which the real load needs, hence the separate pass). This surfaced ~20k dropped rows in `financials_2013`-`2017` and ~1,444 in `qualified_donees_2014/2017/2018` — but a follow-up investigation found the original "non-UTF-8 bytes" explanation only covers **half** of these, and the "obvious" fixes don't actually work:
   - **`financials_2013`-`2016` (confirmed genuine encoding issue).** These files are not UTF-8 at all — every accented French character is single-byte Latin-1/CP1252 (`\xe9`="é", `\xe0`="à", confirmed byte-for-byte; zero legitimate multi-byte UTF-8 sequences exist anywhere in these files). But DuckDB's own `read_csv(..., encoding='latin-1')` parameter, reproduced cleanly across fresh connections, returns the **exact same row count** as the current broken UTF-8 load — zero rows recovered — even though a plain Python `bytes.decode('latin-1')` correctly recovers every affected line. Why DuckDB's `encoding=` flag doesn't do the transcode a plain per-line Python decode does is unresolved; a Python pre-processing pass (read raw bytes, decode with a fallback chain, write a cleaned UTF-8 file, then let DuckDB read that) is the more promising path, not yet implemented or verified.
   - **`financials_2017` and all three `qualified_donees_2014/2017/2018` files (different root cause — NOT encoding).** Every line in these files decodes as valid UTF-8. DuckDB's actual reject reason is `TOO MANY COLUMNS` (confirmed via `store_rejects`) — a CSV quote/dialect-detection problem (e.g. `"Morningstar Mission, Napanee, ON"` not being recognized as one quoted field in some rows). `financials_2017` fails DuckDB's `sniff_csv` dialect auto-detection outright. Two candidate fixes were tested and **neither is safe to apply uniformly**: forcing `quote='"', escape='"'` recovered +381/+317 rows on `qualified_donees_2017`/`2018` but **lost 51,148 rows on `financials_2017`** (worse than doing nothing); DuckDB's own suggested `strict_mode=false` recovered +7,504 rows on `financials_2017` but **reduced row counts on both `qualified_donees_2017` and `2018`** (301,889 vs baseline 302,901, and 296,339 vs 298,472) — meaning it's silently changing which rows are treated as valid, not simply recovering the ones currently rejected, plausibly via null-padding misaligning columns rather than genuinely fixing them. No single setting fixes all four files without a regression somewhere.
   
   Not yet addressed: a per-file fix (Python pre-decode for the encoding files; targeted, row-level-verified dialect handling for the quote-mismatch files) rather than one blanket setting. Given this data feeds dollar-value calculations, a fix should not be applied without row-level verification that it doesn't silently misalign columns — the `strict_mode=false` result above is exactly that failure mode observed directly, not a hypothetical risk.

2. **Numeric-suffix fuzzy-match false positive — fixed, with one confirmed small residual gap.** `ALBERTA CIRCUIT 5A OF JEHOVAH'S WITNESSES` was matching `Alberta Circuit 7A of Jehovah's Witnesses` at a 97.4 `token_sort_ratio` score — branch/circuit/chapter/district numbers barely affected the score in an otherwise-long, otherwise-identical name. Fixed by a digit-token gate: `Resolver.resolve()` now requires a candidate's digit-bearing tokens (`digit_tokens()`, whitespace-split so `5A` stays distinct from `5B`/`7A` — a `\d+` regex would collapse it to `5` and reintroduce the bug) to exactly match the incoming record's before scoring; the existing `FUZZY_ACCEPT`/`FUZZY_REVIEW` thresholds are unchanged and apply on top. A follow-up on the first full run found two false-reject patterns (8.6%/13.9% of that run's 1,492 gate rejects), both fixed with `_fuse_digit_letter_tokens()` (joins a split digit+single-letter suffix, `1-B`→`1B`, back together before comparison) and `digit_tokens_match()` (ignores a year-like token, `YEAR_RE` 1800-2099, when only one side carries one, but keeps it as a differentiator if both sides carry a *differing* year).

   On the first full run with both refinements in place: **1,164 gate rejects**, and a full regression scan (recomputing pre-refinement digit-token equality against every one of them) found **3 of 1,164 (0.6%)** where the fusion refinement itself newly rejects a pair the simpler pre-refinement logic would have matched — manually reviewed, not just counted. 1 was a confirmed genuine regression and a new failure mode: a T3010 donee-name field truncated mid-word right after a digit (`"...Saskatoon School Division No. 13 T"`, cut off before `TRUST FUND`) got its truncated single letter fused onto the digit (`"13"`+`"T"`→`"13T"`), no longer matching the untruncated registry name's bare `"13"` — confirmed recurring (multiple donee records for the same org truncated at exactly 60 chars), not a one-off. The other 2 were genuinely ambiguous (JW circuit `1`/`1-B`, `2`/`2-A` pairs) rather than confirmed regressions, since this same dataset has confirmed-different lettered JW sub-circuits elsewhere (`5A`/`7A`, `11B`/`1B`) — left alone.

   **Truncation regression — fixed.** `_fuse_digit_letter_tokens()` now takes the raw (pre-normalization) name length and drops — rather than fuses — a trailing single letter when that length lands exactly on `RAW_NAME_TRUNCATION_LEN` (60 chars, the length 34,395 distinct qualified-donee raw names hit in the current build — a real cliff, not a coincidence). 5. **Fuzzy-match blocking silently missed real charities when a source record's province was blank, and bilingual "English/French" CRA names never matched a same-org record naming just one language — both fixed.** Found investigating why POP Montreal International Music Festival showed up as 5 separate entities instead of 1.

   **Province-blank blocking gap.** `Resolver.resolve()`'s fuzzy candidates are blocked by `(province, name-prefix)` via `block_key()`, with no fallback when a record has no province. T3010 donee-name fields routinely lack one: `t3010_non_qualified_donee` has no province/city column in the CRA source at all, and `t3010_qualified_donee`'s is frequently empty even with a donee name present (confirmed: 3 of 4 real POP Montreal donee rows had `Province` = NULL). A blank-province record's block key (`"|POP "`) landed in a different bucket than the charity's own key (`"QC|POP "`, seeded from its registered province) — the fuzzy matcher never even considered the correct candidate, regardless of name similarity. Fixed with a second index, `fuzzy_index_by_prefix` (name-prefix only, spanning all provinces), consulted only when the incoming record's province is blank; records that do carry a province keep the original `(province, prefix)` blocking unchanged.

   **Bilingual "/"-name scoring gap.** `normalize_name()` already split grants.csv's `"English|French"` pipe format (issue #3), but the CRA T3010 registry uses a different bilingual convention, `"English Name/Nom français"` (POP Montreal's own legal name: `"POP MONTREAL INTERNATIONAL MUSIC FESTIVAL/FESTIVAL INTERNATIONAL DE MUSIQUE POP MONTREAL"`), left untouched by that split — a short, single-language donee name scored only 25-65 (`token_sort_ratio`) against the full concatenated bilingual string, nowhere near the 90-point `FUZZY_ACCEPT` threshold, regardless of blocking. Fixed with a new `name_variants()` helper (mirrors `discovery/match.py`'s existing `_name_variants()`, which needed the identical fix for its own separate matcher): `add_charity()` now indexes the full name plus each half of a bilingual "/"-name as its own fuzzy candidate, all resolving to the same `entity_id`. Low blast radius: for the large majority of charities with no "/" in their legal name, `name_variants()` returns the name unchanged.

POP Montreal specifically: 5 entities (1 charity + 4 unmatched duplicates across canada_council/federal_gc/both T3010 donee schedules) down to 2 — the real charity (now absorbing every name variant via `exact_bn` or `fuzzy_accept` at score 100) plus one remaining residual, `"POP Montreal "` alone — too short/generic to safely fuzzy-match at high confidence without risking false positives elsewhere; an intentional, unfixed gap, not a regression. Regression tests: `tests/test_province_blank_fuzzy_fallback.py` (5 cases, CI-enforced), including one confirming the digit-token gate (issue #2) still applies on the province-blank fallback path.

## Live Web App

`analysis/webapp.py` is a small local Flask server that queries `nonprofit_network.duckdb` directly on each request, instead of the pre-generated static HTML below. A deliberate architecture change from the rest of this repo's "self-contained HTML, no dependencies" pages, made because the static search indexes below had to cap at the top 50,000 orgs / 40,000 grant texts (embedding the full corpus as JSON produced 105MB / 44MB files) — querying live removes both the cap (every search runs over the full corpus) and the "does this detail page exist yet" problem (static pages need `--all` batch generation first; here every page renders on demand).

```bash
.venv/bin/python analysis/webapp.py                # http://127.0.0.1:8931
```

Routes: `/` (home), `/orgs` + `/orgs/search.json` (live org search, reusing `org_page.py`'s rendering), `/orgs/<slug>` (org detail page), `/grants` + `/grants/search.json` (live grant-text search), `/grants/<hash>` (detail page, reusing `grant_search.py`'s rendering), and `/hidden-nonprofits` (see below).

**Org detail pages use lazy-loaded receipt drawers, unlike the static pages.** Rendering an org page eagerly (the static approach) computes up to 300 receipt-drawer lookups per page, and `locate_t3010_qd_receipt` measured at ~0.15s/call — turning a live page load into 30-50+ seconds for any org with a large qualified-donee category (not just huge regranters like The Salvation Army; The Canadian Red Cross Society hit 44s). Live org pages instead render claims with `data-lazy`/`data-grant-id` and skip the eager query entirely; `toggleDrawer()`'s JS fetches `/orgs/<slug>/receipt/<grant_id>` only when a drawer is actually clicked open, and caches the result client-side so re-toggling doesn't refetch. `org_page.py`'s `render_page()`/`render_grants_table()` take a `lazy_receipts` flag controlling this (default `False`, unchanged for the static generator); confirmed fix: The Canadian Red Cross Society's page went from 44s to ~0.1s.

**Every lazy grant claim shared the same drawer id — a real reported bug, fixed.** `render_grants_table()` computed each row's `drawer_id` as `f"drawer-{len(drawer_ids)}"`, but lazy rows deliberately never append to `drawer_ids` (that's the whole point of lazy mode — no eager receipt query). So `len(drawer_ids)` stayed frozen at whatever it was before the loop started, for every lazy row — not just within one grant-category table, but across every `lazy_receipts=True` call sharing that same list, i.e. the entire org page. In the browser: click the first grant, its receipt loads and caches under `id="drawer-N"`; click any *other* grant afterward, and `toggleLazyDrawer()`'s `getElementById('drawer-N')` finds that same cached element and just re-toggles it — the first grant's receipt, forever, no matter which grant is clicked. Fixed by keying `drawer_id` on `table_id` (already unique per `(direction, category)` section — see the `render_grant_sections` call site) plus each row's own position within its table, both known without touching the shared, lazy-row-blind `drawer_ids` counter at all. Verified against the real Salvation Army page (600 lazy claims, previously all sharing one id, now all distinct) and by clicking two different grants and confirming their drawers are genuinely different DOM elements, not just visually similar content. Regression tests: `tests/test_org_page.py` (`test_lazy_receipts_each_grant_gets_a_distinct_drawer_id`, `test_lazy_receipts_distinct_ids_hold_across_multiple_categories` — both confirmed to fail against the pre-fix code before being confirmed to pass against the fix).

**Org pages now surface `discovery/`'s non-charity nonprofit identification — the first time that work reaches a visitor at all.** Before this, REQ's and Corporations Canada's discovery output lived only in `discovery/output/*.csv`; nothing in `analysis/` read those files, so none of that matching work was visible on the live site despite being fully built and validated (see the "Quebec Non-Charity Nonprofit Discovery" section below). `org_page.load_discovery_index()` reads both `*_discovery_flagged.csv` files directly (read-only, no coupling to `nonprofit_network.duckdb`'s schema) and builds `entity_id -> match info`, cached once per app lifetime the same way `get_link_manifest()` already is (`webapp.py`'s `_state`/`get_discovery_index()`). `render_page()` takes an optional `discovery_index` param; when the current entity is in it, the header gets a second clickable badge next to the existing `entity_kind` one (e.g. `"Confirmed Quebec nonprofit — not a registered charity"`), which opens a drawer explaining the match, exactly like every other claim on the page.

Deliberately scoped narrow, not every discovery row: only `charity_status == "non_charity_nonprofit"` **and** `federal_grant_status == "federal_grant_match"` rows are included. Two reasons, not one: (1) a discovery record with no confirmed federal grant link was never resolved into `entities` at all, so there's no existing page to attach a badge to — surfacing those would mean deciding whether to create entities for them, a bigger, separate decision not made here; (2) `needs_review` rows are excluded on purpose, since this is a live public page, not an internal review queue — only auto-accepted matches are shown as fact. A `registered_charity` discovery match is also excluded from this first pass: that entity's `entity_kind` is already `'charity'` (`KIND_LABELS` already renders "Registered charity"), so a discovery-source annotation there is lower-value and left for later if wanted. Wired into all three page-rendering entry points (`webapp.py`'s live route, `build_all_pages`, and the single-page `build_page` CLI), all reading the same cached index. Regression tests: `tests/test_org_page.py` (8 new cases — badge presence/absence, source-specific copy, and `load_discovery_index()`'s CSV filtering).

**A confirmed real overlap between the two discovery sources, found while building the summary stats below — 235 entities are independently matched by *both* REQ and Corporations Canada** (a federally-incorporated nonprofit that also registers to operate in Quebec, most likely). `load_discovery_index()` originally stored one `discovery_source` string per entity, so whichever file loaded second (`corporations_canada_discovery_flagged.csv`) silently overwrote REQ's entry for every overlapping entity — the deduplicated entity count/dollar total were still correct (an entity was never double-created), but REQ's true reach was undercounted by exactly 235 in any *by-registry* breakdown. Fixed by tracking a `discovery_sources` set per entity (all confirming registries) alongside the single `discovery_source` (first-confirmed, still used for the org-page badge, which shows one source not an exhaustive list) — `fetch_discovery_summary()` now counts an entity under every registry that confirmed it, so by-source counts can (correctly) sum to more than the deduplicated total. Verified: REQ's by-source count went from an undercounted 5,388 to the true 5,623 after the fix. Regression test: `tests/test_org_page.py`'s `test_load_discovery_index_entity_confirmed_by_both_sources_is_not_dropped`.

**`/orgs` search now has a "confirmed non-charity nonprofit" filter** (`NON_CHARITY_FILTER_KEY = "nc"` in `webapp.py`) — the discovery badge was previously only visible if you already knew which org page to visit; this lets a visitor browse the whole confirmed set (~9,580 organizations) at once. Deliberately implemented as a separate code path from the existing `_ORG_FILTER_COLUMNS` category filters (received-as-qualified-donee, given-as-government-funding, etc.): those are SQL boolean flags computed from `grants_unified` via a shared subquery join; "confirmed non-charity nonprofit" isn't a database column at all, it comes from `discovery/`'s output CSVs, so it's applied as a plain `entity_id IN (...)` condition instead (`entity_id` values are always trusted ints from the CSV, never user input, so this is safe to inline directly rather than pass a ~9,580-item parameter list). A matched search result's kind label also switches from the generic entity_kind label to "Confirmed non-charity nonprofit" so results are self-explanatory without opening each one. Regression tests: `tests/test_webapp.py` (5 new cases).

**`/hidden-nonprofits`** is a new page telling the story this whole `discovery/` effort was building toward: computed live via `org_page.fetch_discovery_summary()` (never hardcoded, so the numbers can't go stale the way a hand-written figure would the next time either the entity graph or `discovery/` gets rebuilt) — total confirmed non-charity nonprofits, total federal dollars they've received, a by-registry split, and the ten largest by total flow as recognizable, linked examples (Canadian Institute for Health Information, Mitacs, Genome Canada, Manitoba Métis Federation, and similar — real organizations most visitors would assume are charities). States its own coverage limits plainly (REQ is Quebec-only, Corporations Canada is federal-incorporation-only — most provincially-incorporated nonprofits outside Quebec aren't covered by anything here) rather than implying a national count. Linked from the homepage. Regression tests: `tests/test_webapp.py` (4 cases) and `tests/test_org_page.py`'s `fetch_discovery_summary()` cases (3 cases).

**`/regranting-network`** visualizes a structural pattern no single org page shows: money passing *through* a regranting intermediary (an org that's a significant funder AND significant recipient at once — `entity_role_summary.role = 'dual_role'`, e.g. The Salvation Army, United Way of Greater Toronto, UHN Foundation) on its way to smaller downstream nonprofits. `org_page.fetch_regranting_network()` picks the top N `dual_role` entities by total flow (default 8) plus their top M funders/recipients each (default 4, long tail collapsed into a single "N other funders/recipients" node per intermediary); `render_regranting_network_svg()` lays it out as a hand-rolled Sankey-style flow diagram — three columns, node height proportional to flow, links as cubic-bezier ribbons proportional to dollar amount — no charting library, same "self-contained HTML, no dependencies" convention `render_timeline()`'s funding-history bars already follow.

**Self-loops are excluded, and confirmed real, not hypothetical.** The Salvation Army's own entity is its own largest nominal "funder" and "recipient" ($900.5M) — almost certainly an internal-transfer/allocation artifact in the source data — filtered out (`funder_entity_id != recipient_entity_id`) since a node can't meaningfully flow into itself on a network diagram regardless of cause. A funder or recipient shared by more than one intermediary (e.g. a federal department funding several different regranting charities) becomes one shared node with multiple links, deliberately not deduplicated into separate per-intermediary copies — that convergence is itself part of the structural picture.

**Node links use the real `link_manifest` (entity_id → slug), not a bare `slug_for(name)` call — confirmed necessary, not just cautious.** `slug_for()` alone doesn't handle two different entities whose names produce the same slug (`build_link_manifest()`'s entire job); calling it standalone from inside the SVG renderer risked a node silently linking to a different organization's page on a collision. Synthetic "N other funders/recipients" nodes (`entity_id: None`) are never wrapped in a link at all, since there's no real page for them.

First real run: 78 nodes (37 funders, 8 intermediaries, 33 recipients), 79 links — a legible, bounded diagram, not the full graph. Linked from the homepage. Regression tests: `tests/test_org_page.py` (9 cases, against an isolated in-memory fixture with a crafted self-loop/shared-funder/long-tail scenario — the shared fixture DB has no `dual_role` entities) and `tests/test_webapp.py` (2 cases, route wiring only).

Not a regression from the category split above (which caps the *combined* embed budget the same as before it existed) — a pre-existing cost at this specific scale, surfaced while building the split. `--all` over the full ~533k-entity corpus is correspondingly impractical without addressing this first; not attempted.

## Grant Text Search (self-contained HTML, no dependencies)

`analysis/grant_search.py` answers a different question than the org pages above: not "who is this organization" but "what was this grant for." Grant descriptions are heavily templated (same insight `classify_l2.py` is built around), so it indexes **distinct** `(source_dataset, normalized description, normalized program_name)` texts, not the ~5M individual grant rows — of those ~5M rows, 3.77M (`t3010_qualified_donee`/`t3010_non_qualified_donee`) have no real free text (`program_name` is a single constant label, `description` is always `NULL`), so only `federal_gc` and `otf` are indexed (~192.7k distinct texts, ranked by total dollar amount).

```bash
.venv/bin/python analysis/grant_search.py --index                  # docs/grants/index.html (fast, ~1s)
.venv/bin/python analysis/grant_search.py --all                    # batch-generate detail pages (~10s, bulk-fetched)
.venv/bin/python analysis/grant_search.py --text-hash <16-hex-hash> # one detail page
```

Search (`docs/grants/index.html`) combines a text query (substring over program name + description) with optional source checkboxes (Federal G&C / Ontario Trillium Foundation), same AND-combined pattern as the org search. Capped to the top `DEFAULT_GRANT_INDEX_LIMIT` (40,000) texts by total amount by default, same "stated plainly, not silently truncated" reasoning as the org index (uncapped: ~44MB). Each result links to a detail page (`grant-<16-hex-hash>.html`) listing every grant sharing that text — funder, recipient, amount, fiscal year, cross-linked to `../orgs/<slug>.html` — using the same `SCALE_CAP`/`VISIBLE_ROWS` collapse pattern as the org pages.

`text_hash` is `sha256(normalized_description + " " + normalized_program_name)`, same normalization convention as `classify_l2.py`'s own `text_hash` (whitespace-collapsed), so a future join against `l2_text_classifications` could attach L2 subject codes to a detail page without recomputing anything — not implemented, kept compatible on purpose. **Batch generation must group all qualifying grants once and match them against the index in memory** (`fetch_all_grants_grouped_by_hash`), not re-query per text (`fetch_grants_for_text`, a full-table hash scan, fine for one on-demand lookup but ~0.6s × 40,000 texts ≈ 7 hours if looped) — confirmed the hard way before switching to the bulk approach (~10s for all 40,000). A related bug caught by the same rebuild: grouping the index query by *raw* description text while `text_hash` normalized whitespace let two rows differing only in e.g. a double space become two separate index entries whose stats undercounted what their (correctly merged) detail page actually showed — 347 of a requested 40,000 detail pages silently didn't match any index entry before the fix; index and detail generation must group on the identical normalized expression. Regression test: `tests/test_grant_search.py`'s `test_index_and_bulk_fetch_use_identical_hash` and `test_whitespace_variants_collapse_into_one_distinct_text`.

Four committed samples under `docs/grants/` (of the 40,000 that `--all` generates locally — only these four are checked in, same "curated samples, not the full batch" convention as `docs/orgs/`): `grant-37350e1e7360081f.html` (Canada Housing Infrastructure Fund, 9 grants — small, multiple provincial/municipal recipients, cross-links to org pages), `grant-bc6751591061367e.html` (Interim Housing Assistance Program, 37 grants — exercises the 30-row "Show more" collapse), `grant-41b8d52f186a1d48.html` (Youth - Canada Summer Jobs, 186,975 grants / $2.3B / 57,445 recipients — exercises the 300-row `SCALE_CAP` and its rollup note), `grant-dbc7b66a3aa958a4.html` (an `otf` example, since the other three are all `federal_gc`).

## L2 Service Classification

`analysis/classify_l2.py` assigns Candid PCS Subject codes to **distinct** federal grant
description texts (not every grant row -- descriptions are heavily templated, so dedup first,
classify each distinct text once, propagate to every grant sharing it). Two interchangeable
backends: Anthropic (`claude-haiku-4-5-20251001`, needs `ANTHROPIC_API_KEY`) or a local Ollama
model (`--backend ollama`, no key, no cost -- used for the pilot since no Anthropic key was
available; see the Decisions note in `docs/l2-classification-spec.md`). Quote/code enforcement
is mechanical and backend-independent: a `quote` that isn't a verbatim substring of the input,
or a code not in the taxonomy, downgrades the result to `abstain` with an explicit flag rather
than trusting an unverifiable classification. `--max-calls` is a required hard cap; results are
resumable, keyed by `(sha256 of normalized text, prompt_version)`, in
`evidence/l2_classifications.duckdb` (not `nonprofit_network.duckdb`).

```bash
.venv/bin/python analysis/classify_l2.py --dry-run --max-calls 1100
.venv/bin/python analysis/classify_l2.py --backend ollama --limit 1000 --max-calls 1100   # the pilot
```

Pilot (1,000 texts, Ollama qwen2.5:7b) results: `docs/l2-pilot-report.md`. The pipeline stops
after the pilot by design -- scaling to the full ~160K distinct-text corpus is a separate,
future instruction, not something this script does on its own.

## Non-Charity Nonprofit Discovery (`discovery/`)

New module answering a different question than the rest of this repo: not "who moves money" (the entity graph above) but "does this legal nonprofit exist, and is it a registered charity or not." Full design: `docs/montreal-discovery-spec.md` (kept its original filename; the pilot it describes has since scaled to the whole province — see below). Phase 1 (charity-status flag) and Phase 2 (social-purpose flag) are both implemented **and have now been run province-wide** against a real REQ export (2026-07-01 snapshot) for Quebec; Phase 3 (scale beyond Québec) is now started too, via a second, national data source — see "Corporations Canada national discovery" below — though it's an additive complement to REQ, not a replacement (see its coverage caveat).

```bash
.venv/bin/python discovery/run.py --req-dir path/to/unzipped/req/export                        # Phase 1 only, all of Quebec (default)
.venv/bin/python discovery/run.py --req-dir path/to/unzipped/req/export --with-social-signal    # + Phase 2
.venv/bin/python discovery/run.py --req-dir path/to/unzipped/req/export --region montreal       # original pilot's island-only subset
```

No REQ data is bundled or downloaded by this repo — point `--req-dir` at the directory a real Registre des entreprises (Données Québec) export unzips to (must contain `Entreprise.csv` and `Nom.csv`). Requires `nonprofit_network.duckdb` to already exist and not be held by a concurrent writer, since `discovery/ingest/cra.py` and `discovery/ingest/grants.py` connect to it read-only.

**First real run (2026-07-01 REQ snapshot), Montreal-only pilot, Phase 1:** 16,237 active Montreal-region NPOs (`COD_FORME_JURI='APE'`, `COD_STAT_IMMAT='IM'`) against 6,457 Montreal-region CRA charities. Blocking-level breakdown: 8,523 matched via postal code, 7,706 via FSA fallback, 8 via city only.

**Spec step 7 (validation on a labeled sample) run for real, and it found a real bug in the matcher — not just a threshold to tune.** A manually-reviewed stratified sample (68 rows spanning the needs_review band, the auto-accept boundary, and both auto-decided buckets) found `discovery/match.py`'s `token_set_ratio` scoring genuinely unrelated organizations as high as real matches whenever they merely shared one common word: **27 of 30 sampled needs_review rows were wrong** (e.g. "Centre de la Petite Enfance Origami" matched to "...de McGill", sharing only the generic daycare-category prefix), and **4 of 8 sampled rows just above the 90 auto-accept cutoff were also wrong** — meaning the *auto-accepted* `registered_charity` output had real false positives silently mixed in, not just an overly-cautious review band.

Root cause: `token_set_ratio`'s token-intersection algorithm inflates similarity whenever names share even one word, regardless of whether that word is a generic category term ("Centre," "Église," "Club," a city name) or a genuine identifier. Fixed in two parts (both in `discovery/`, not the main entity graph, which has its own separately-validated normalizer/thresholds — see Deviations below): switched scoring to `token_sort_ratio` with bilingual `/`-split-aware comparison, and added `normalize_for_scoring()` — a matching-only normalizer (never used for display/entity keys) that strips a data-driven list of ~30 generic Quebec-nonprofit category words (`MONTREAL`, `CENTRE`, `ÉGLISE`, `CLUB`, `PETITE`, `ENFANCE`, ...; frequency-derived from a real 22,694-name sample) plus French connector words and elision remnants ("L'Institut" was tokenizing to `["L", "INSTITUT"]`, with the stray "L" itself inflating unrelated scores in 1–11% of names).

**Re-validated against the same 68-row sample before rebuilding**: max score among confirmed-wrong pairs dropped to 81.6 (was up to 91.5, above auto-accept); min score among confirmed-correct pairs held at 85.4+ — a clean gap, no overlap. **Full rebuild, same REQ snapshot:** 3,685 registered_charity (was 4,200) / 12,269 non_charity_nonprofit (was 11,202) / 283 needs_review (was 835). Spot-checked fresh samples of both buckets post-fix: `registered_charity` is now dominated by clean exact/near-exact matches; `needs_review` now holds genuinely ambiguous cases (an alumni association vs. its university, a parents' association vs. its college) rather than pure category-word coincidences. Regression tests for the specific false positives found: `tests/test_discovery_match.py`, `tests/test_discovery_normalize.py`.

**Scaled to all of Quebec (2026-07-16), same REQ snapshot.** `--region` now defaults to `"quebec"` (province-wide, via CRA's own `Province` field — `discovery/config.py`'s `QUEBEC_PROVINCE_CODE`) rather than the Montreal-island subset; pass `--region montreal` to reproduce the original pilot's narrower filter (`_in_montreal()`/`MONTREAL_ISLAND_MUNICIPALITIES` kept for that purpose in `discovery/ingest/cra.py`). **Full province run, Phase 1:** 58,749 active Quebec NPOs against 18,969 Quebec CRA charities → 11,576 `registered_charity` / 44,440 `non_charity_nonprofit` / 2,733 `needs_review`. Blocking-level breakdown: 31,878 postal / 25,851 FSA / 37 city / 983 no blocking key.

Scaling up surfaced two real performance bugs, both fixed in `discovery/`, neither a threshold or design change:

- **`normalize_for_scoring()` re-normalized the same organization name from scratch on every single discovery-record × candidate comparison inside a matching block**, rather than once per distinct name. Fine at Montreal-pilot scale; at province scale the largest blocking bucket alone (Montreal-area records against Montreal-area CRA charities) made this the dominant cost. Fixed by wrapping it in `functools.lru_cache` (`discovery/normalize.py`) — no output change, just memoized.
- **Phase 2's social-purpose match had no blocking at all** — every `non_charity_nonprofit` discovery record was compared against the *entire national* federal G&C social-signal candidate list (440,846 rows), an unblocked cross product that took hours and didn't finish at province scale (44,440 × 440,846 ≈ 19.6 billion comparisons). Fixed two ways: `discovery/ingest/grants.py`'s `load_federal_social_signal_candidates()` now takes a `province` filter applied in SQL (`run.py` always passes `"QC"`, since REQ is Quebec-only — cut the candidate pool to 85,368 before any matching starts), and `SocialSignalCandidate` now carries `city`/`province` (+ an always-`None` `postal_code` for shape-compatibility) so `run.py` can reuse `discovery/block.py`'s postal→FSA→city cascade for the social match exactly as it already does for the charity match. **Full province run, Phase 2, on the 44,440 non-charity set:** 150 `social_purpose` / 484 `needs_review` / 43,806 `not_social`. Total runtime for both phases combined: ~30 seconds (was: didn't complete in 47+ minutes before the first fix, still running past 4.5 hours before the second).

**Region**: `discovery/config.py`'s Montreal-island constants (`MONTREAL_ISLAND_MUNICIPALITIES`, `MONTREAL_FSA_PREFIXES`) are kept for `--region montreal`, the original pilot's narrowest, least-ambiguous reading of "Montreal" (city of Montreal + the 15 never-remerged demerged municipalities, with an `H1-H4`/`H8-H9` FSA fallback) — see the spec's own flagged region-definition risk. The province-wide default instead uses CRA's own `Province` field directly, which is simpler and more reliable than any municipality allowlist.

**Deviations from the original spec, and why:**

- **CRA lookup reads `raw_t3010_ident` in `nonprofit_network.duckdb`, not the resolved `entities` table and not `data/t3010/identification_*.csv` directly.** `entities`/`entity_financials` never persisted postal code (only city/province), but postal code is this module's primary blocking key. Re-parsing the raw per-year CSVs directly would risk reintroducing the encoding/dialect row-drop problems in open issue #1 above in a second, less-hardened code path — `raw_t3010_ident` is already loaded through the hardened, reject-counted `_load_t3010_table()` loader, so `discovery/ingest/cra.py` reads that instead.
- **`status` (active/revoked) is a heuristic, not a real field**: identification schedules carry no such flag, so a BN whose latest row isn't in the most recent year present is treated as no-longer-current — the same inference `build_entities_and_grants()` already relies on implicitly.
- **`discovery/normalize.py` imports `normalize_name`/`display_name`/`LEGAL_SUFFIXES`/BN helpers from `analysis.build_entity_graph`** rather than reimplementing them, specifically to avoid two normalizers producing different match keys for the same org name. The one deliberate addition is `ENR` (Québec's common registered-sole-proprietorship suffix) on top of the existing suffix set.
- **`discovery/ingest/grants.py` reads `grants_unified`** (already deduped to the latest amendment per `(owner_org, ref_number)`) rather than re-parsing `grants.csv`, so it doesn't reinherit the ~1.7x amendment-double-counting bug fixed under open issue #3 above.
- **`SOCIAL_PROGRAM_NAME_KEYWORDS` in `discovery/config.py` is a starting keyword list, not a validated taxonomy.** Before hand-growing it, check whether `analysis/classify_l2.py`'s Candid PCS subject-code classifications can answer "is this program social" directly — same classification problem, already partly solved elsewhere in this repo. Not done yet because the L2 pilot only covers a 1,000-text sample (`docs/l2-pilot-report.md`), not the full corpus.
- **Tests live in `tests/test_discovery_*.py`, not `discovery/tests/`** as the spec's file tree suggested, so they're actually picked up by the documented `pytest tests/` command and by `.github/workflows/tests.yml` (which invokes that exact path).
- **REQ ingestion rewritten against a real export — the original placeholder assumption (one denormalized CSV, columns like `"Nom"`/`"Municipalité"`/`"Code postal"`) was wrong about the file shape, not just the column names.** The real dataset is several relational files joined by `NEQ`: `Entreprise.csv` (one row per company; `COD_FORME_JURI` is a *code* needing a `DomaineValeur.csv` lookup — confirmed `'APE'` is the only code meaning "Personne morale sans but lucratif", matching the spec's scope exactly, not also `'ASS'`/Association; postal code is its own clean field, `ADR_DOMCL_LIGN4_ADR`, no parsing needed; city is *not* a separate field — it's whichever of `LIGN2`/`LIGN3` is the last non-null line before the postal code, since an intervening floor/suite/PO-box line shifts the real city from `LIGN2` to `LIGN3`) and `Nom.csv` (one row per name; `TYP_NOM_ASSUJ` codes — `N`=legal name, `A`=trade name, `M`=an auto-assigned numbered-company placeholder name, excluded — have no `DomaineValeur.csv` entries and were inferred from real sample rows instead). Also added an active-status filter (`COD_STAT_IMMAT='IM'`) not in the original placeholder, since the pilot's question ("does this legal nonprofit exist") is present-tense — a struck-off entity doesn't currently answer it, unlike CRA's revoked-but-still-informative status. See `discovery/config.py`'s `REQ_*` constants and `discovery/ingest/req.py`'s docstring for the full detail; regression tests in `tests/test_discovery_req_ingest.py`.
- **The spec's "retain other establishment addresses for matching" is a known gap, not implemented**: `discovery/ingest/req.py` dedupes multiple establishments per NEQ down to one primary address plus a merged trade-name set; secondary addresses are currently dropped rather than fed into `discovery/block.py`/`discovery/match.py`.
- **`discovery/normalize.py`'s `normalize_for_scoring()` is a separate function from `normalize_org_name()`, not an extension of it**, even though the fix it enables (stripping generic category words before fuzzy-scoring two names) would have been simpler to add directly to `normalize_org_name()`. Deliberate: `normalize_org_name()` is pinned by an existing test to match `analysis.build_entity_graph.normalize_name()` behavior exactly (minus the `ENR` suffix), and that shared normalizer's stopword set is load-bearing for the main entity graph's own already-validated `FUZZY_ACCEPT`/`FUZZY_REVIEW` thresholds -- changing it would risk shifting match decisions across the whole ~530k-entity graph in ways nothing here re-validates. `normalize_for_scoring()` is used only inside `discovery/match.py`'s `score_names()`.
- **Output filename renamed from `montreal_discovery_flagged.csv` to `quebec_discovery_flagged.csv`** (`discovery/output.py`) since the default run is now province-wide; `charity_needs_review.csv`/`social_needs_review.csv` are unchanged since they were never region-named.
- **`load_cra_records()`'s `region_filter: bool` param became `region: "quebec"|"montreal"|None`** (`discovery/ingest/cra.py`) when the province-wide filter was added, since a plain boolean no longer says which region `True` means. `load_req_records()`'s `region_filter: bool` param (`discovery/ingest/req.py`) was deliberately left alone — REQ data is Quebec-only regardless, so `False` there already meant "no narrower filter," i.e. all of Quebec — renaming it to match `region=` would have been churn with no behavior change.

### Corporations Canada national discovery (`discovery/run_cc.py`) — Phase 3

A second, independent discovery source alongside REQ, using Corporations Canada's federal not-for-profit registry instead of a provincial one. **Coverage caveat:** this only covers *federally*-incorporated nonprofits (Canada Not-for-profit Corporations Act) — most local/regional Canadian nonprofits incorporate provincially, not federally, so this is an additive national source for federally-chartered orgs, not a substitute for a REQ-style registry in every province. `docs/montreal-discovery-spec.md`'s `DiscoveryRecord` shape already anticipated this ("Adding a province means writing a new ingest adapter against this shape, not touching the matcher") — implemented as a new `bn` field (default `None`, so REQ/tests are unaffected) rather than a province.

```bash
.venv/bin/python discovery/run_cc.py --cc-csv data/corporations-active-non-cbca-en.csv
```

Data: the "Other active corporations" bulk CSV from Corporations Canada's [Federal Corporations open-data dataset](https://open.canada.ca/data/en/dataset/0032ce54-c5dd-4b66-99a0-320a7b5e99f2) (not bundled/auto-downloaded by this repo, same convention as REQ — download `corporations-active-non-cbca-en.csv` to `data/`). Confirmed against a real 2026-07-16 snapshot (50,665 total rows): the file bundles not-for-profit corporations together with cooperatives, boards of trade, and a handful of special-act corporations in one file — `discovery/ingest/cc.py` filters to `Governing legislation == 'Canada Not-for-profit Corporations Act'` only (49,431 rows), mirroring REQ's narrow one-legal-form scope. Unlike REQ, `Governing legislation` is a plain readable string, not a code needing a `DomaineValeur.csv`-style lookup table.

**The key structural difference from REQ: 99.0% of NFP Act rows carry a Business Number directly** (48,950 of 49,431) — REQ carries none at all. That BN enables an exact-match fast path (`classify.classify_charity_status_by_bn()`) that resolves ~99% of records against the CRA registry with no fuzzy-matching ambiguity whatsoever, before falling back to REQ's postal→FSA→city cascade only for the BN-less remainder — the same exact_bn-first, fuzzy-fallback order `analysis.build_entity_graph.Resolver.resolve()` already uses for the main entity graph.

**A second bug found and fixed before trusting the output: fuzzy matching can produce a false positive when ground truth is available to contradict it — something REQ never had to guard against since it had no BN at all.** First real run: 11,487 `registered_charity`, 304 `needs_review`. Manually inspecting fuzzy-matched (non-exact-BN) records revealed 371 cases auto-accepted as `registered_charity` (343 of them a perfect 100 name-score match) where the record's *own* real BN did **not** match any CRA charity — direct evidence contradicting the fuzzy match, silently overridden by name similarity. Root cause, confirmed on real examples: a nonprofit "society" and its separately-incorporated affiliated "foundation" share a near-identical name but are genuinely distinct legal entities — e.g. `"The Advocates' Society"` (BN `108070707`, not a charity) fuzzy-matched `"The Advocates' Society Foundation"` (BN `848687091`, a real charity) at 100; the Foundation is the charity, the Society itself is not. Fixed with `classify.reconcile_bn_conflict()`: downgrades a fuzzy `registered_charity` classification to `needs_review` (`review_flag="bn_contradicts_fuzzy_match"`) whenever the record carries its own non-matching BN — but only the auto-accept bucket; `needs_review`/`non_charity_nonprofit` are left alone since there's no silent false acceptance to correct there, and a BN-less record (REQ, or any future BN-less source) is a complete no-op. **Re-run after the fix:** `registered_charity` 11,487 → 11,116 (−371, exactly the confirmed conflict count), `needs_review` 304 → 675 (+371). Regression tests: `tests/test_discovery_cc_ingest.py` (9 cases) and `tests/test_discovery_classify.py`'s BN-fast-path and `reconcile_bn_conflict` cases (7 new).

**Full run, match method breakdown:** exact_bn 10,963 · fsa 25,009 · postal 13,435 · city 22 · no blocking key 2. **Charity status breakdown (post-fix):** non_charity_nonprofit 37,640 · registered_charity 11,116 · needs_review 675. Output: `discovery/output/corporations_canada_discovery_flagged.csv`, `discovery/output/charity_needs_review.csv` (same `discovery/output.py` writer as REQ, with a new `charity_match_method` column — `"exact_bn"`/`"fuzzy"`/`None` — added to `OUTPUT_FIELDS` so every row is auditable by which mechanism resolved it, mirroring `entity_links.match_method` in the main entity graph).

Phase 2 (social-purpose signal) not run against this source yet — `discovery/ingest/grants.py`'s social-signal candidate loader currently filters to `province=` a single province (REQ always passes `"QC"`); Corporations Canada spans every province, so it would need either no province filter (national cross product — same unblocked-cost problem Phase 2 hit at Quebec scale, worse nationally) or per-record province-scoped blocking. Not investigated.

**Linking every record to federal grant totals (`discovery/run_cc.py --with-federal-grant-match`).** Same goal as REQ's own federal-grant-match stage below, but structurally different because ~99% of records already carry a BN: `classify.classify_federal_grant_match_by_bn()` resolves the vast majority via a direct, zero-ambiguity BN lookup against `entities.bn_root` (covering both `charity` and `other_org` entity kinds, since a charity's own grant total is just as directly answerable by BN) — REQ's fuzzy fallback (name-prefix blocking, national candidate pool since Corporations Canada spans every province) is only reached for the small remainder with no BN of their own, gated to the `non_charity_nonprofit` set exactly like REQ's own stage.

**A second false-positive class, distinct from REQ's, found and fixed before trusting the output — this time NOT catchable by the collision detector.** First real run: 6,832 `federal_grant_match`, zero collisions (`reconcile_grant_match_collisions()` from the REQ fix reused as-is). But splitting the bucket by exact-BN vs. fuzzy-fallback revealed 1,343 records — far more than expected — went through the fuzzy path (most scoring a perfect 100 on name alone, without BN backing). A spot-check of 12 real fuzzy matches scoring *below* 100 found roughly half wrong: `"Harbour Authority of Westport"` wrongly matched `"...of Newport"`; `"Opportunify"` wrongly matched `"Opportunity International Canada"` ($22.1M at stake); `"Hungarian Canadian Medical Association"` wrongly matched `"HUNGARIAN - CANADIAN MEDIA CORPORATION"`; `"The Stellar Foundation"` wrongly matched `"Stella's"`. None of these collided with a second claimant, so `reconcile_grant_match_collisions()` correctly didn't (and structurally can't) catch them — this is a *different* failure mode from REQ's: a **unique**, non-duplicate wrong match, arising because this candidate pool is matched nationwide with no province restriction (unlike REQ's Quebec-only, mostly postal/city-blocked pool), so name-prefix blocking alone lands a much larger, more heterogeneous set per block. REQ's own post-collision-fix fuzzy matches (scores 95-98) were separately spot-checked and found all genuinely correct — this problem is specific to Corporations Canada's larger, unblocked-by-province pool, not a REQ regression.

Fixed with `classify.reconcile_low_confidence_grant_matches()`: downgrades any fuzzy `federal_grant_match` scoring below 100 to `needs_review` — **applied only in `run_cc.py`, deliberately not in REQ's `run.py`**, since REQ's sub-100 fuzzy matches don't show this failure pattern and tightening them the same way would only lose real matches for no precision gain. Matches scoring exactly 100 (perfect normalized-name equality, whether BN-backed or not — e.g. `"CANADA MEDIA FUND"` vs. `"CANADA MEDIA FUND CORPORATION"`, $1.7B) weren't part of the failure pattern and are left alone.

**Re-run after both fixes, verified rather than assumed:** sub-100 matches confirmed **0** (checked directly), collisions confirmed **0**. `federal_grant_match` 6,832 → **6,634** (−198, the confirmed sub-100 count exactly). **Final validated numbers: 6,634 organizations** (2,386 already-charity, 4,192 non-charity, 56 needs-review-charity-status) **linked to federal grants, 42,980 grant records, $61.49B total** — split roughly $54.2B exact-BN-backed (zero ambiguity) and the remainder perfect-name-match fuzzy. A fresh spot-check of 12 post-fix matches were all genuinely correct. Regression tests: `tests/test_discovery_classify.py`'s `classify_federal_grant_match_by_bn` (3 new) and `reconcile_low_confidence_grant_matches` (5 new) cases.

### Linking REQ to actual federal grants (`discovery/run.py --with-federal-grant-match`)

REQ's Quebec NPOs were never linked into `nonprofit_network.duckdb` in either direction — `discovery/run.py`/`ingest/cra.py`/`ingest/grants.py` only ever *read* the database, they never write an `entity_id` back for a REQ record. So there was no way to ask "how much did REQ-confirmed Quebec non-charity nonprofits actually receive in federal grants" — Phase 2's social-signal match only checks whether an NPO's name/city loosely resembles the recipient of a *socially-themed-sounding* federal program, which is a suggestive signal, not a real grant link.

**The key insight, confirmed on real data before building anything:** `analysis/build_entity_graph.py`'s `Resolver` already creates an `entities` row for *every* federal_gc grant recipient, not just charities — a recipient that doesn't match a CRA charity falls through to a residual `other_org` entity regardless of what it is. So Quebec's non-charity federal grant recipients already exist in the database; the real task was matching REQ's list against entities already there, not creating a new link from scratch. Checked before designing anything: 50,204 `other_org` entities in Quebec alone received a federal_gc grant (151,876 grant records, $107.4B) — and that pool is **not** nonprofit-filtered at all (real sample: `"la Récolte de la Rouge SENC"`, `"Ferme Agri-Valleyfield S.E.N.C."` — farms and ordinary businesses, not missed nonprofits). REQ's own list (`COD_FORME_JURI='APE'`, already filtered to legally-incorporated Quebec nonprofits) is exactly the right instrument to answer "which of these 50,204 anonymous grant recipients are confirmed real nonprofits" — genuinely new information, not redundant with anything federal_gc's own data can answer alone.

**The blocking problem this pool creates.** These residual `other_org` entities carry **province only, never city or postal code** (confirmed against real rows, not assumed — `Resolver`'s residual branch only ever stores `province` on `EntityRow`). `discovery/block.py`'s postal→FSA→city cascade degrades to one province-wide bucket for a pool like this — an REQ-record × 50,204-candidate match would collapse to a single Quebec block, the same unblocked-cost wall Phase 2 hit before its own fix, except with no BN to shortcut it (unlike Corporations Canada). Fixed with a new opt-in **name-prefix blocking tier** in `discovery/block.py` (`name_prefix()`, `build_name_prefix_index()`) — only tried as a last resort after postal/FSA/city, and only when a `name_prefix_idx` is explicitly passed, so Phase 1's existing CRA-charity matching (which already succeeds via postal/city almost always) is completely unaffected. Mirrors the exact `(province, first-4-normalized-chars)` blocking `analysis.build_entity_graph.Resolver.resolve()` already uses for the identical "no postal available" reason (see the province-blank fuzzy-blocking fix earlier in this file).

**New pieces, mirroring existing patterns throughout `discovery/`:**
- `discovery/ingest/grant_recipients.py` — `load_federal_grant_recipient_candidates()`, a read-only query joining `grants_unified`/`entities` for `source_dataset='federal_gc'`, `entity_kind='other_org'` (charity excluded — already covered by Stage 1), optionally province-filtered, aggregated to grant count + total dollars per entity.
- `discovery/classify.py`'s `classify_federal_grant_match()` — same three-bucket shape (`federal_grant_match`/`needs_review`/`no_match`) as `classify_charity_status()`, same `AUTO_MATCH_SCORE`/`NEEDS_REVIEW_FLOOR` thresholds.
- `discovery/run.py --with-federal-grant-match` — runs only on the `non_charity_nonprofit` set (same gating as `--with-social-signal`), writing `matched_grant_entity_id`/`matched_grant_entity_name`/`federal_grant_match_score`/`federal_grants_received`/`federal_dollars_received` columns (added to `OUTPUT_FIELDS`) plus a new `federal_grant_needs_review.csv` (only written when the flag is passed — `write_outputs()`'s `federal_grant_review_filename` param defaults to `None`).

**First real run (2026-07-01 REQ snapshot) found a real false-positive class — found, fixed, and verified, not just flagged.** 58,749 Quebec NPOs against 50,204 `other_org` federal_gc recipients → 5,878 auto-accepted `federal_grant_match`. Spot-checking that bucket surfaced generic-name collisions the `token_sort_ratio` + `MATCHING_CATEGORY_WORDS` stopword list (built from a REQ-vs-CRA-*charity* sample) doesn't cover for this different candidate-pool vocabulary: **111 grant-recipient entities were each claimed by 2–6 *different* Quebec nonprofits** — impossible, since one entity can't be six different real-world organizations. Worst case: `"Le club des 50 ans et plus"` (a Golden Age Club with no town name in its own registered name) claimed by 6 different town-specific clubs (Ste-Jeanne-d'Arc, St-Bruno-de-Kamouraska, St-Anaclet, St-Agnès-de-Rimouski, St-Jean-de-Dieu, Les Bons Amis), sharing only the generic "club"/"age d'or" phrase. Also: `"RÉSEAU CENTRE"` (5 claimants, sharing only "réseau"/network), `"Chambre de commerce et d'industrie Les Moulins"` (4 claimants, sharing only the generic chamber-of-commerce phrase). No amount of stopword tuning fixes this class — several of these candidates' own registered names carry zero town-specific information to match against in the first place, so the ambiguity is inherent to the data.

**Fixed with a structural safety net, not a threshold tweak:** `classify.reconcile_grant_match_collisions()` — a post-pass over every discovery record's classification (not a per-record decision, since collision detection requires seeing every match first) that downgrades *every* `federal_grant_match` whose `matched_grant_entity_id` was independently claimed by more than one discovery record to `needs_review`. With no reliable signal to say which (if any) claimant is correct, all colliding claims are downgraded rather than guessed at — same "don't silently assert a shaky match" philosophy as `reconcile_bn_conflict()` and the rest of this module, just applied across records instead of within one. Required restructuring `discovery/run.py`'s main loop to collect all `federal_grant_cls` into a list before building any `row_dict`, since the reconciliation pass needs the full picture first.

**Re-run after the fix, verified rather than assumed:** collision count confirmed **0** (re-checked directly against the output, not just inferred from the count drop). `federal_grant_match` 5,878 → **5,623** (−255, matching the confirmed-collision-involved record count almost exactly). The specific known-bad example was traced end to end: `"TRANSPORTEURS EN VRAC DE LA RÉGION 04 INC."` (a regional trucking association) had wrongly matched `"Les Transporteurs en vrac Région 03 inc."` at 96.4 — a different region's association, the exact same "numbered branch/chapter" false-positive class the digit-token gate protects against in the main entity graph (`analysis/build_entity_graph.py`), which `discovery/match.py` doesn't implement. Confirmed post-fix: correctly caught and downgraded to `needs_review` (it collided with a second claimant, `"LES TRANSPORTEURS EN VRAC DE LA RIVE-SUD"`, over the same candidate). A fresh random sample of 15 post-fix auto-accepted matches were all genuinely correct on inspection (town/org-specific identifying details align on both sides, not just generic-phrase overlap).

**Final numbers, verified:** **5,623 confirmed Quebec non-charity nonprofits** matched to federal grant recipients, **25,682 federal grant records**, **$7.80B total**. Regression tests: `tests/test_discovery_classify.py`'s `reconcile_grant_match_collisions` cases (7 new — two-way and three-way collisions, list order/length preservation, `None`/`no_match`/mid-band entries passing through unaffected).

**Known remaining limitation, not chased further:** the collision detector only catches *duplicate* claims on the same candidate — a false positive where exactly one discovery record uniquely (and wrongly) claims a candidate is still possible and wouldn't be caught (e.g. a still-generic-but-uncontested match). The digit-token gate itself (not just this collision-detector workaround) was considered but not ported into `discovery/match.py` — would need its own validation pass against this module's real data before landing, same caution `analysis/build_entity_graph.py`'s own gate got. `discovery/normalize.py`'s `MATCHING_CATEGORY_WORDS` stopword list also hasn't been re-derived for this candidate pool's different vocabulary (réseau, chambre de commerce, âge d'or/50 ans et plus) — a real, deferred improvement, not attempted here since it needs its own frequency-based validation rather than an ad hoc addition from a handful of examples.
